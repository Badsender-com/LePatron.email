# Skills are feature skills or task skills, and skills and expertises have an audience

- Status: proposed
- Date: 2026-10-29
- Epic: #1290
- Extends: ADR 0012
- Amended by ADR 0019 (on a copy, an item has the audience production gives it; a feature skill's draft may name a schema its code does not declare yet)

The expertises and skills the platform company writes are meant to reach the client companies through MCP, and many will have no LePatron feature behind them, at first or ever. The skills written so far show two kinds that the app did not tell apart. **A feature skill** is a pure function a LePatron feature calls: an input template, an input and output schema declared in the code, a JSON output contract the server checks (the subject and preheader generation, the spelling correction). **A task skill**, most of them, is a procedure written for an assistant: read a report the user provides, review an email against a checklist. It takes files, runs steps and a quality check, produces a deliverable, and has neither template nor schema. Both stay one entity, versioned, rated and logged the same way; the nature says how the skill is served.

**The nature belongs to the version**, a feature one unless the version says otherwise. Turning a feature skill into a task skill, or back, is writing a draft version of the other nature and publishing it, under the publication checks of that nature: a task skill's version needs its procedure. The active version is never changed after the fact, and the one it replaces stays, archived. An archived version is never published again (only a draft is): going back is duplicating it into a new draft, then publishing that draft. Whatever asks a skill's nature, the MCP catalogue first, reads that of its active version. The mark that offers a feature skill to assistants stays on the skill, and counts only while its active version is a feature one.

**Through MCP**, a task skill is a prompt the user picks, a resource the assistant reads, and a result of `find_skills`, so that an assistant can pick it itself when the request calls for it: an MCP prompt is only ever chosen by the user. A task skill names, in order, the expertises it consumes, and its prompt embeds their active versions: the procedure runs as the platform company wrote it without the assistant having to look for them. Each is named once. One that is not published, or that is kept to the platform company while the skill is open to all, is left out of what an assistant receives: publishing the skill warns of it, without refusing it. A feature skill is served only when a super admin marks it so, with arguments taken from its schema when the code has one, from the placeholders of its template otherwise, and never its JSON output contract, which only LePatron reads. In the app, the feature that calls it composes the expertise it applies; through MCP no feature does, so its prompt and its resource tell the assistant to find them with `find_applicable_expertises` before running it. Publishing a skill for assistants needs no deployment.

**Skills and expertises are written in French**, and stay so, whatever language their readers speak. The MCP server tells every assistant so in its instructions: apply them as they are, answer in the user's language, search the skills with French words, and give the expertise lookup the language of the email, which may differ from the user's. Finding a skill does not depend on one language: `find_skills` matches the identifier too, and when nothing matches it lists every skill for the assistant to choose from their descriptions. Translating each skill and expertise was rejected: every version would have to be written, reviewed and published in every language, for assistants that already translate what they read.

**Every skill and expertise has an audience**: the platform company alone, while it is tried, or every company. A new one starts with the platform company, whose team uses and proves a first draft before opening it; the audience is the gate between a draft that works and one the client companies get. Publishing a version and setting the audience are two acts: the first decides what is active, the second who gets it. They stay two acts when they travel in one request, a publication that also opens the item to every company.

**Opening a task skill to every company offers to open the expertises it consumes kept to the platform company**, those the assistants of the other companies would otherwise follow it without. Each is offered on its own, unchecked at first: opening an expertise also applies it, at once, in the editor of every company, which is a choice of its own. With none checked, the skill opens without them. The other way, keeping an expertise to the platform company again warns of the open task skills that consume it, which the client companies then receive without it. Neither warning refuses the change.

**The audience applies wherever a skill or an expertise is used**, in the editor as through an assistant. An expertise kept to the platform company never shapes a client company's generation in the editor, nor reaches its assistant. A feature skill kept to the platform company is available to the platform company alone, in the editor too: the server refuses to run it for a client company's member, and the editor hides the buttons that call it there rather than letting them fail, a part that comes with the text generation features (#1145 and after). A task skill has no path in the editor, so its audience gates assistants only. A call whose company is not known is treated as a client company's; the super admins' playground sees everything, as the platform company does. MCP access stays a gate of its own, the company's (ADR 0012): it opens the assistant path, never a skill or an expertise whose audience is closed to the company.

**An audience is set, never assumed.** A client company gets what is open to every company, and nothing else, so a skill or an expertise without an audience stays with the platform company. The platform company is the audience of a new one, set when it is created, never filled in when an existing one is read and saved again: an old record would otherwise close itself without anyone deciding it. The skills and expertises that existed before the audience are opened to every company at deployment.

A brand charter is not a skill with a narrower audience: it is a company's writing guidelines, which belong to its CRM governance.

## Considered Options

- **A setting per skill and expertise for where it is served** (in the app, through MCP, both): rejected. No expertise written so far had a reason to stay out of MCP, and the one feature skill that should (the spelling correction, whose input the editor builds) is covered by the mark on feature skills. What does vary is who may use it.
- **An audience applied through MCP only**: rejected. An expertise still tried by the platform company would shape the client companies' generations in the editor, and a feature skill still tried would run behind their buttons: the gate between a draft and what clients get would hold on one path out of two.
- **A feature skill kept to the platform company that client companies still run in the editor**: rejected, the audience would mean one thing for a feature skill and another for the rest.
- **The nature set on the skill**: rejected. Changing it would change at once how the active version is served, without a publication, its checks, or a way back.
- **Prompt arguments from the code's schema registry only**: rejected, a skill for assistants would wait for a deployment, and task skills have no schema.
- **The expertises of a task skill found by scope and category** (`findApplicable`): kept for feature skills, rejected for task skills, whose procedure reads named expertises in a given order.
- **Audiences of chosen client companies**: not now; the case that called for them, client brand charters, goes to the CRM governance.

## Consequences

- The skills and expertises back office gains the nature of a version, the procedure of a task skill, its ordered expertises, the mark of a feature skill and the audience (#1344, #1345). What is still kept to the platform company is marked in the lists, and publishing it reminds that it stays so, since forgetting to open it is the likely mistake.
- The skills and expertises that exist get every company as audience, by a migration run at deployment, so that the first MCP version behaves as decided in ADR 0012. Until it runs, the client companies get none of them, in the editor or through an assistant.
- Until the editor hides them (#1145 and after), a client company's member who uses a button whose skill is kept to the platform company gets a refusal.
- Bringing the skills and expertises written outside LePatron into it is an epic of its own: it reclassifies as expertises the "skills" that are knowledge, sets each one's nature, audience and consumed expertises, and moves client charters to the CRM governance.
