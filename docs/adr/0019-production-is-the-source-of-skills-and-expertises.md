# Production is the source of skills and expertises; copies follow it, and what a feature uses is guarded

- Status: proposed
- Date: 2026-11-05
- Epic: #1420, #1421, #1422
- Amends: ADR 0013 (one doctrine, thin skills; an audience a copy receives; a feature skill drafted before its code), ADR 0014 (an assistant may publish and change an audience, in two steps), ADR 0018 (a copy follows production, which wins)

Loading some sixty skills and expertises written outside LePatron, then moving them to a test instance, showed two blocks. Every imported item arrived as a draft to publish by hand, one by one. And the platform company's team, who want to improve their skills and expertises every day from an assistant, could only draft there, then go to the back office to publish. Behind both: no instance was the reference, and a skill that a feature uses was treated like any other, so the only safety was to change nothing.

**Production is the source.** The platform company's team writes, publishes and opens skills and expertises to clients in production, from the back office or from an assistant. Staging and development are **copies**: they receive what production holds, and what is tried on them never goes back up.

**A feature skill can be born in production before its code.** A new AI feature's skill is written in production as a draft no client sees, and goes down to the developer's copy by the follow. Its draft may name an input or output schema that production's code does not have yet: saving it warns, and a badge stays on the draft for as long as the schema is missing from the instance's code. Publishing it is refused, with a message that says why, until the code that declares the schema is deployed on that instance. Only a draft is so relaxed: an active version always has its schema, so a feature never calls a skill whose contract its code cannot check. A file import (ADR 0018) still blocks a skill whose schema is missing.

## A copy follows production

**How.** A copy pulls production, on demand from its back office, and every night where its instance turns the nightly follow on. It reads with a read token that a super admin creates in production's back office and gives to the copy, configured with production's address in the copy's environment. A token reads every skill and expertise production holds: drafts, items kept to the platform company, test cases included. It is given only to a copy whose super admins may read all of it. Narrowing what a token reads (only what is active and open to clients, for instance) is left for later. Creating and revoking a token record who did it, and a security event. A copy creates no token: a copy is never a source, so copies do not chain.

**An item that came from production follows it in everything**: its active version, its draft, its audience, its archived state, whether it is served to assistants, its identity (title, description, category, scope), with production's version numbers. A field of its identity emptied in production is emptied on the copy too, rather than kept as the copy had it. There is no "copy ahead" that keeps its own any more: a copy shows what clients live. Each version the follow writes is marked as received from production (`followedAt`), and so is the item, with the date of the last follow that touched it.

**The copy's own work is never lost.** When the follow has to replace something written on the copy, that content goes, as a draft, into a **new item of the copy**, which the follow never touches. There are two such cases: a draft written on the copy when production brings a draft, and a version published on the copy. The new item's identifier is the original's with a stable suffix (`<id>.copie`, `<id>.copie-2`), its title the original's followed by "(travail de la copie)", its audience the platform company alone, and it is not served to assistants. The follow's report links to it. A draft written on the copy stays where it is as long as production brings none.

**What production removes, the copy removes, if it got it from production.** A draft production deleted, or an item never published that production deleted, disappears from the copy when the copy had received it by a follow. What the copy wrote itself is never deleted. An item written on the copy is left alone as long as production has no item with its identifier; once production has one, the item follows production, and its work on the copy moves to a separate item, as above.

**The first follow of a copy that already holds items.** A staging that existed before the follow holds items imported by file or written there, none of them marked as received. Its first follow takes over every item whose identifier production also has: from then on it follows production, and a local active version that differs from production's moves, as a draft, to an item of the copy's work, like any work of the copy. A staging that drifted from production holds many such items after its first follow: nothing is lost, and the report lists each one. Before that first follow, a super admin may keep any item on the copy, followed or not, to leave it out of the take-over. Until a first follow succeeds, the copy's items say that they are not followed yet.

**Keep on this copy, follow production, duplicate on this copy.** On a copy, a super admin may keep a followed item on the copy: the follow no longer touches it, and its report only says that production changed it. Following production again attaches it back; at the next follow, the copy's work on it goes into a new item, as above. Publishing a followed item on a copy offers "Keep on this copy", checked by default, since whoever publishes on a copy most likely wants to keep what they publish. Published with the box unchecked, the item keeps following production: until the next follow it serves the version published on the copy, then that version moves, as a draft, into a new item of the copy, and the item takes production's back. Duplicating on the copy creates an item of the copy holding the chosen version as a draft, to try something without touching the follow. A copy that was ahead is now either kept on the copy, by choice, or follows production, with its work set aside in a new item; nothing is kept silently.

**Item by item, and the report says what happened to each.** The follow first reads and validates production's whole answer, then writes each item on its own, on the condition that it did not change since it was read: an item written meanwhile, in the back office or by an assistant, fails with its reason rather than be overwritten. A failure stops nothing else. The report says, for each item, whether it was added, updated, already up to date, kept on the copy (and whether production changed it), moved (the copy's work set aside, with the new item), removed, or failed, with its reason, and warns, for instance, of a task skill whose expertise is missing on the copy. A copy whose code lacks a schema that one of production's active versions names fails that item until the code is deployed.

**The follow speaks its own format.** Production's answer carries a format number of its own, distinct from the export file's: the two change for different reasons. One module produces it on production and reads it on the copy, so they cannot drift apart. A copy also accepts the previous format number, since during an acceptance round its code is often newer than production's. An item the copy cannot read is refused alone, not the whole answer.

**The nightly follow is set per instance, and one follow runs at a time.** The web server runs no timer: the hosting platform's scheduler runs the follow every night (`clevercloud/cron.json` on Clever Cloud, `cron.json` on Scalingo), and the follow runs only on an instance where an environment variable turns it on, which the copy's back office shows. A follow in progress is recorded in the database when it starts, with an expiry so that a process that dies does not hold it for ever; a second follow, from the button, the nightly command, another process or another instance of the same application, is refused while it holds. The lock only keeps two follows from running at the same time. Clever Cloud runs a scheduled task on every instance of an application, and those may start minutes apart, one after the other has finished: a nightly follow is therefore skipped when another nightly follow started less than 60 minutes ago, so the night follows once. The record is also the follow's trace.

## A version's state, and the level LePatron works out

A version is a draft, active, or archived, and an item may be archived too; the follow carries each of these states. The published version keeps the name "Active". Active is not open to clients: the audience stays the gate between what the team uses and what clients read through MCP (ADR 0013), so a version can be proven inside the platform company before every company reads it. **Used by a feature** is not a state anyone sets: LePatron works it out from the expertise filters each feature declares and from the skills features call, so it cannot be forgotten or wrong.

**The doctrine lives in the expertises.** The platform company's know-how is written once, in expertises, and improves continuously; skills stay thin. A feature skill and a task skill on the same subject read the same expertises, as the subject line generation and the subject line task already read the subject line doctrine. A feature reads the active version of its expertises at every call: a doctrine improved in production reaches the feature at once, with no developer, years after the feature was written. A skill with two faces, a contract for the feature and a procedure for an assistant, was rejected: one version would hold two contents to keep in step, and the doctrine, which is what matters, is already shared.

**Publishing what a feature uses is guarded, not blocked.** When the version about to be published is used by a feature, LePatron first replays the **test cases** of the feature skills concerned with it, and shows each one before and after. The person decides: a failure warns, it does not block, since an AI's output has no automatic pass or fail. Test cases live in the feature skill's version, where the model already keeps them: they travel with an export and a follow, and any successful run of the playground can become a test case. Blocking on a failed case was rejected for that reason; the activation impact alone was rejected because it lists what changes without showing how.

**What the guard covers, and what it does not.** A publication is guarded on what uses the item once published: an archived item, used by no feature, goes through the guard when it is published again. The replay is bounded: a cap of AI calls, said before it runs, and a few calls at a time; the cases past the cap are named, not replayed. The guard is a task of the server: starting it answers at once, with what it will replay, and whoever started it reads it again until it is done, with the before and after, or failed; no request of the back office or of an assistant waits for the AI. The guard, once done, answers a key bound to the versions it ran on, as they were, and to the person; the publication requires it and records what the key carries, never what a page declares. A change that ends or starts a feature's use without a new version, the scope or the category of an active expertise, or an archive, is not replayed: it warns of the features it reaches and is kept on the item, and archiving a skill a feature calls is confirmed explicitly first. A batch holds skills or expertises, not both: an expertise and the skill that reads it are published in that order.

## An assistant may publish and open, in two steps

With the `skills:write` scope (ADR 0014), an assistant used by whoever may manage the platform may now publish a draft and change an audience. Both go in two steps. The first call changes nothing: for a publication it runs the guard and answers the before and after; for an audience it answers what clients will read once it changes. Each answers a key for the change it describes. The second call, with that key, applies the change, and is refused if what was checked changed in between.

**What the confirmation proves.** The second call comes from the model, not from a button: it proves that the change applied is the one that was described, not that a human read the description. Both tools are marked destructive (`destructiveHint`), which asks the client to have the person approve the call, but it is only a hint the client may ignore. The guard stays in front of every publication, the right to manage the platform is checked again at each call, and every publication and audience change is recorded with the user and the connected application. ADR 0014 kept publication and audience in the back office, in human hands; they are now also in the hands of whoever confirms in the conversation, with that limit said.

## What this changes in earlier decisions

- **ADR 0013.** A skill or expertise on a copy has the audience production gives it, not one set on the copy; only an item written on the copy starts with the platform company. A feature skill's draft may name a schema the instance's code does not declare yet; its publication still needs it.
- **ADR 0014.** An assistant no longer only drafts: it may publish and change an audience, in two steps.
- **ADR 0018.** A copy that follows production is linked to it, which ADR 0018 rejected for a one-off transfer between instances: a copy that must follow every day is the case it did not cover. Where an import keeps the target's title, category, scope and audience, a follow takes production's. Where an import blocks two versions with the same number and different content, a follow lets production win, and sets the copy's own version aside in a new item. A file imported by hand keeps the rules of ADR 0018: everything arrives as a draft, for the platform company.

## Consequences

- Three epics, each delivered on its own: a copy follows production (#1420); the guard at publication, the computed level and the replay of test cases (#1421); publishing and audience from an assistant (#1422).
- The back office of a copy shows where each skill and expertise comes from (follows production, kept on this copy, written on this copy, the copy's work), when the copy last followed production, whether the nightly follow is on, and whether a follow is running. Production's back office lists the read tokens.
- The test cases of the feature skills that exist are to be written before the guard can say anything for them.
