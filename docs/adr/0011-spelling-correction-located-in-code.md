# Spelling correction is a text generation action whose corrections the code places

- Status: proposed
- Date: 2026-10-12
- Epic: #1251
- Amended: 2026-11-23, after the epic's review (the whole email corrected by batches of blocks, a rewriting flagged)
- Amends: ADR 0016 (three skills in text generation, each action offered when its own skill runs; the correction's whole email includes the header and the footer; a targeted field is corrected even at its sample value)

Correcting the spelling, grammar and typography of a field, a block or the whole email is an AI action of text generation, run by a Badsender skill on the group's text generation engine, with no new AI feature and no external proofreading service. The skill reads the visible text of each field, its merge tags protected, and answers corrections — the field, the text before, the text after, the reason —; it never sees nor returns the HTML. The code finds each "before" in the text nodes of the field and replaces it there only, and drops a correction it cannot find, finds twice, that straddles a tag or touches a merge tag. The panel lists the corrections to accept or ignore one by one, a new family of steps next to proposals; an accepted correction is written into the email at once and undone with the editor's own Ctrl+Z, and one not found anymore at that moment, because the text changed since, is not applied.

## Considered Options

- **An external proofreading service** (LanguageTool, Antidote), plugged in as an integration like DeepL for translation: reliable on spelling, but outside the skills and their logs, without Badsender's doctrine, with a second contract, and with no way for consultants to tune it.
- **A typography expertise per language**: Badsender cannot write and maintain one for every language its clients write in. The skill corrects by the conventions of the text's own language; an expertise of scope `correction` can still be added later, without code, for a rule of the house.
- **A new "Correction" AI feature**, enabled on its own: every action would then become a feature to configure. Correcting is still writing text the user accepts; a finer control of which AI actions a group exposes will come as such.
- **Letting the model rewrite the HTML of the field**: shorter, but a broken tag or merge tag would go unnoticed into the email. Placing the corrections in code means a mistake straddling a tag is not corrected, which is rare.
- **The whole corrected text as one proposal to apply**: the user could not refuse one change and keep the others.

## Consequences

- A correction is launched by every role that may edit an email's content, the reviewer excepted, as every AI action is (ADR 0010).
- Never through MCP as an action: ADR 0012 lets no assistant write an email, and placing the corrections is the editor's work. The correction skill is not served to assistants either: its contract means something only with the code that places its corrections.
- Each AI action is offered when its own skill runs for the company, not when every skill of text generation does: the correction skill can be published after the subject's and the preheader's without taking anything from them.
- The whole email is corrected by batches of consecutive blocks, within the caps of one request (40 fields, 5,000 characters a field, 50,000 in all), each batch about 6,000 characters of text: a model reading a long request misses more mistakes. The skill still reads one list of fields, each under a key unique in the request, and the server puts each correction back on its block. A batch that fails is taken again block by block, so a faulty block loses only itself; a block too large for one request is sent alone, in parts, and the fields of a part that fails are said unchecked. One invocation per block, as first built, made 30 requests for an email of 30 blocks, a pause of a minute past 20, and repeated the instructions and the expertises with every block; by batches, an email that size takes one to four, depending on its text.
- A correction request may take up to 90 seconds, against 30 for other skills: a ceiling, not a wait, since a lot of several thousand characters takes a model longer than a subject; past it, the lot is taken again block by block.
- A failure of the feature itself (switched off, unavailable, signed out, no network) stops the whole email; any other failure is the block's. When the AI rate limit stops it, the panel waits for the delay the server gives and sends the refused request again, if that delay is short; a longer one stops it. The batches count against the group's text generation rate limit: that pause is the answer to it, not a larger limit for this action. The user can stop at any time, a pause included, and keeps what was found.
- Going back to a correction shows it again without running it again; "Relancer l'analyse" starts over, "Reprendre" goes on with the email from the first block not done. The correction of the whole email is kept apart from that of a block or a field.
- The whole email of the correction holds the header and the footer, where the legal mentions are, unlike the text that generation reads (ADR 0016); the subject and the preheader field are not part of it. Fields still holding the template's sample text are left out of a block or the whole email, and said so; a field the rendering hides is left out quietly; a field the user targets is corrected all the same, sample text included.
- Only the expertise of scope `correction` is read: the transversal writing principles would push the skill towards rewriting. The skill manifest declares it, so the activation alert agrees.
- A correction that changes more than 3 words, compared one by one with their punctuation and spaces aside, is a rewrite: the server returns it marked `rewrite: true`, and the panel marks it "Réécriture", left out of "Tout accepter"; it can still be accepted on its own. The code thus keeps the promise of no change of style or meaning without losing a correction.
- Placing a correction refuses more than a missing or repeated excerpt: a correction that brings a merge tag the text did not have, a control, invisible or bidirectional character, or an excerpt straddling two lines. The merge tags recognized are those of the quality control's shared module (`packages/shared/quality/merge-tag-syntax.js`), so the two never disagree on what a merge tag is. A correction is already present only when it differs from the text by its spaces alone (a non-breaking space the model could not see): that is no loss, and is not counted.
- A non-breaking space reaches the skill as `{nbsp}`, and comes back so: the model can neither write the character nor tell it from a space, so it proposed spaces it called non-breaking and missed those already there. The code turns the marker back into the character before placing anything.
- An accepted correction the editor's undo took back shows as undone, and can be accepted again; Ctrl+Z (⌘Z) in the panel undoes in the editor.
- A field is targeted from the element being edited: its DOM id is matched against the text fields of its block. The AI button comes first in the text editor's toolbar, which is wider than a narrow canvas; on an element no field matches, it opens the block.
