# MCP server: inside the app, with its own authorization server, read-only first

- Status: proposed
- Date: 2026-10-15
- Epic: #1290
- Supersedes the approach of issue #955 (standalone server, API key per group)

LePatron exposes an MCP server so that the AI assistants its users already work with (Claude, ChatGPT, Microsoft Copilot) can read LePatron on their behalf: the Badsender expertises and skills, and the user's own mailings. It is sold as a subscription, to the platform group and to client groups alike, and switched on per group by MCP access: off unless a super admin, or the group's tech admin as part of its AI features, turns it on for a group (`group.manage-tech`, ADR 0004). The first version only reads; writing waits for the server to enforce what a writer may touch (#1103, ADR 0004).

**It runs inside the Express app**, mounted on `/mcp`, not as a standalone service sharing the database. Every tool goes through the same services and access checks as the REST API (workspace and folder membership, `userHasAccessToAllWorkspaces`, the roles of ADR 0004), so no access rule is written twice.

**LePatron is its own OAuth 2.1 authorization server**, embedded in the app. The login it shows is the existing one (local password or the group's SAML), followed by a consent screen. An external identity provider would have had to send users back to LePatron anyway, and would add a third party processing personal data. Because Claude, ChatGPT and Microsoft do not register clients the same way, the server accepts three: Client ID Metadata Documents, open Dynamic Client Registration issuing a client secret (Microsoft 365 Copilot does not take public clients), and clients pre-registered by hand (Copilot Studio in manual mode). A client registered by hand belongs to a company: its tech admin, or a super admin, registers it in the company's settings, because the assistant behind it is set up by that company's IT for its own users. Only that company is offered at its consent, and `/mcp` refuses its tokens for any other. A platform-wide client, registered by a super admin alone, was rejected: it would let any company's users connect through another company's assistant, and would make every company wait on Badsender. It is built on `oidc-provider`, which serves the three natively; its maintained major requires a current LTS, so the app moves from Node 18 to Node 24 (#1337) before the authorization server lands; Node 24 also lets the CommonJS app `require()` that ESM-only package. Writing our own token storage and rotation on Node 18 was rejected: more security code of our own, to keep a runtime that is already out of support. Access tokens last an hour, refresh tokens rotate and last 30 days each, and a connection lasts 90 days at most, after which the user connects the assistant again; consent is asked at every connection, and only the scopes this server knows are accepted (`mcp:read`, `skills:write`), so a client asking for others (`openid`, `offline_access`) is refused. The tokens are signed with keys of the deployment (`lepatron_mcpOauthJwks`): the server does not start without them outside development, since oidc-provider's own development keys are published. No other site may frame the authorization server's pages, the consent page included, and the SAML login carries the way back to the consent page in its RelayState, the only thing the identity provider's cross-site answer brings back. Revocation: the user revokes a connected application from its own page, reached from the sidebar (the app has no profile page), and the group's tech admin revokes all of a group's from its MCP access settings, where the retex is allowed and the clients registered by hand are reached: everything MCP is one section of the AI features page, the tech admin's. Each consent is recorded as a connected application, and `/mcp` checks that record at every call: a revoked application is refused at its next call, before its access token expires, and its refresh tokens are revoked with it. The app's own events revoke the same way: MCP access turned off, a group deleted, a user deactivated or given a new password. Connecting an application again replaces its previous connection to the group, so each application is listed once.

**A token is bound to one user and one group.** A super admin, who has rights on every group, picks the group on the consent screen, like the selected group of ADR 0002; working on another group means connecting again. This keeps two clients' data from meeting in one assistant conversation. On every call the server checks the user's current role, their membership of the group and the group's MCP access, so a change takes effect without waiting for the token to expire. A token's scopes only record what the user consented to (`mcp:read` in this version); what the user may do is asked of the permissions module on every call, from the capabilities of ADR 0004, like any route of the app. Reading through MCP needs no capability, as reading in the app does not: membership of the group and access to the workspace decide. The write tools will ask for the capabilities that already exist (`mailing.create`, `mailing.edit-content`), so a role is defined once for the app and for MCP.

**What is exposed.** Active versions of expertises (as resources, with their version and update date) and skills (as prompts); a draft only in the drafts mode of a super admin trying it (ADR 0014). Mailings the user can reach, listed through the search across accessible workspaces (ADR 0007, #1144) rather than a listing of its own, and read as extracted text by default and sanitised HTML on request. A mailing's status is derived from its facts and never stored (see `GLOSSARY.md`): LePatron does not know that an email was sent, so no status says so. The `search` and `fetch` tools follow the shape ChatGPT expects. Every tool declares an output schema and answers structured content; every reading tool is annotated read-only, so clients do not ask for a confirmation on each read, and the others (`submit_feedback`, the drafting tools and `use_drafts` of ADR 0014) are not; a list links each mailing as a resource. A mailing's preview is also offered as an MCP App, so the clients that render apps (Claude, ChatGPT, Microsoft 365 Copilot, VS Code) show the email itself in the conversation, sandboxed, while the others keep the text (#1342).

**Reading one mailing (#1304).** A mailing is read by the search's own rule (ADR 0007, `findReadableMailing`): what `list_mailings` would never find, `get_mailing` never reads. This is stricter than the app's preview, which any user of the company may open, member of the workspace or not, because a preview URL is shared to pick a mailing to copy; an assistant answers what a user asked, so it reads what that user lists. The text is extracted from the sanitised preview the app serves; its preheader is the template's own field when it declares one (`preheaderText`), and otherwise the first hidden text before any visible word, hidden the way a preheader is. A preview over 1 MB is not read for an assistant, and the answer says so: sanitising and parsing are synchronous, about a second per megabyte, and real previews weigh 50 to 120 KB.

**Search and fetch (#1305).** `search` answers ChatGPT's `{ id, title, url }`: a mailing links to its editor, so a citation opens it; an expertise links to its `lepatron://` resource, since a reader has no page for it in the app, and its citation is not clickable. A public page per expertise would sell what the subscription sells. Words match whatever their case and accents, in what describes a mailing, never its content.

**It is built on the v2 MCP SDK**, served without state behind one route. The v2 SDK follows the 2026-07-28 protocol and still answers the clients that speak the 2025 versions, which most do today; the v1 SDK will not follow the 2026 protocol and only gets fixes for a few months more. The v2 SDK needs Node 20, which the move to Node 24 (#1337) brings.

**Feedback and retex.** MCP has no feedback primitive and the server never sees the conversation, so feedback is a tool. Its retex part, a session summary written by the assistant, is kept only if the group allows retex and the user agrees to it for that feedback. Calls are logged as metadata only (who, which client, which tool, which objects, how long), never the content returned, and kept for the group's log retention. Calls are limited to 60 a minute per connection and 300 per group, counted in each process's memory: the limit guards against an assistant running away, it is no quota, and the app's workers each count their own. The guard and the log wrap every handler through the SDK's `_wrapHandler`, a private hook, so the SDK is pinned to an exact version and the call log suites fail if the hook goes.

## Considered Options

- **API key per group** (issue #955): rejected, it cannot tell users apart, so it cannot respect workspace rights or roles, and ChatGPT and claude.ai connectors require OAuth.
- **A token covering every group of a super admin**, with a `group` argument on each tool: rejected, an assistant would mix two clients' data in one conversation.
- **A table of MCP scopes per role**: rejected, it would define each role's rights a second time beside the capabilities of ADR 0004.
- **The v1 MCP SDK, which runs on Node 18**: rejected, it stays on the 2025 protocol and its fixes end a few months after the v2 release; starting on it means a migration before the first write tool.
- **A stored mailing status with a workflow**: rejected for this feature, it is a product feature of its own; the derived status can be replaced by it later.

## Consequences

- The MCP server and its authorization server are blocked by the move to Node 24 (#1337).
- `oidc-provider` serves Client ID Metadata Documents as an experimental feature: its version is pinned to a minor.
- A metadata document whose redirect URIs all point to the user's own machine, and which declares no application type, is read as a native client's (RFC 8252 §7.3), so any port of the loopback address is accepted: Claude Code declares `http://localhost/callback` and listens on a port of its choosing. Codes only ever reach the user's machine, and PKCE is required of every client.
- Clients that cannot share the embedded authorization server's registration modes are not supported until one of the three fits them.
- Exposing the expertises in full to subscribers is accepted: their value is in being kept up to date.
- Left for later, for want of clients that support them, and kept possible by the stateless v2 server: the Skills extension of MCP (skills stay prompts), asking the retex consent through elicitation (it stays a tool argument), Tasks for long operations (the write tools will also answer a job to poll), and enterprise-managed authorization.
