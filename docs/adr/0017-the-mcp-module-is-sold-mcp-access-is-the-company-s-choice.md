# The MCP module is what the platform company sells; MCP access stays the company's choice

- Status: proposed
- Date: 2026-11-04
- Epic: #1394
- Amends: ADR 0012 (MCP access as the subscription)

MCP is billed as a flat-rate module. ADR 0012 made MCP access both the thing sold and the thing a company turns on, so a company's tech admin could switch on what nobody had bought. The two are now apart: the **MCP module**, opened or closed by a super admin in the company's Modules, like Email Builder and CRM Intelligence; and **MCP access**, the tech admin's switch in the AI features, unchanged. A company's users connect an assistant only when the module is open **and** the access is on.

**One rule, read where access is already read.** The module is checked where MCP access is: at every `/mcp` call, and when the consent screen picks the companies it offers. The company update still accepts the tech admin's access switch while the module is closed: writing it opens nothing, so the server needs no second rule for a case the interface does not produce. Refusing that write was rejected for that reason. A consent reads the company again once its connection is recorded: a module closed, or an access turned off, while the user consented revokes that connection too, and the consent is refused.

**One rule for the module and MCP access.** The module is one of the company's switches, written as MCP access is: a strict boolean (`true`, nothing else, opens it), set in the one operation that reads what it was, recorded as a security event when it changes (`mcp-module.opened`, `mcp-module.closed`), and the company's connected applications revoked whenever a request closes it, already closed or not, so a revocation that failed runs again. It stays a super admin's (`platform.manage`), and comes with the rest of the Modules form, saved by its button like the modules beside it. A company created with the module open records its opening. Writing the flag as the other modules' was rejected: a value cast by the database could open the module, and a closing would end every connection with no trace.

**A save sends only what the page changed.** Any settings page of the company sends only the fields it changed since it loaded, never the whole company (General and Colors, as the Tracking and Export tabs): a tab left open cannot close a module, nor undo any other change, made elsewhere since. It holds for every module, Email Builder and CRM Intelligence included. The switches saved on their own (MCP access, retex, two-factor authentication) stay as they are.

**No bypass for super admins.** The Email Builder guard lets a super admin through a closed module; MCP does not. A token leaves the app and a connection lasts 90 days: a super admin's assistant reading a company that pays for no module would be an access nobody sees. A super admin who needs to test opens the module.

**Opening does not turn access on.** The platform company sells, the company decides: opening the module leaves MCP access as it was, off for a new company. Turning both on at once was rejected: it would take the decision away from the tech admin, whose switch is the one the users' connections answer to.

**Closing revokes, and keeps the company's choice.** Closing the module revokes the company's connected applications, as turning MCP access off does (ADR 0012): a module no longer paid for must leave no live token, and reopening it must not revive forgotten connections. MCP access itself is left as the company set it, so a reopened module behaves as the company had chosen; its users connect their assistants again. Closing is confirmed at the save, when the module open at the page's loading is now closed, with the number of connections it ends, since unlike the other modules it stops something running. Resetting MCP access on closing was rejected: the company would have to redo a choice it made, for a decision that was not its own.

**Closed, the AI features still show it.** The MCP access section stays in the AI features page, its switch disabled and its settings folded, saying the module is not part of the company's subscription; a super admin also gets a link to the company's Modules. Hiding the section, as a closed module's page leaves the sidebar, was rejected: the tech admin would not know the feature exists, nor whom to ask. The consent screen tells a user whose company lacks the module to ask the platform company, not the tech admin, who cannot do anything about it; a super admin, who opens the modules, is told the module is missing.

**A super admin always reaches the connected applications.** The sidebar link to the connected applications shows for whoever may manage the platform, whatever the selected company has: the page lists their connections in every company, which they must be able to revoke. For every other role it shows when their company has the module and MCP access. The page filters by company, the selected one by default for a super admin, or all, and says so when the company shown lacks the module or MCP access: no assistant can connect to it, and its connections ended when it closed. No history of the revoked connections is kept: the security events record the closing.

**Closed by default, no migration.** Nothing of MCP is in production yet. The platform company's module is opened by hand in each environment, a line of the release checklist.
